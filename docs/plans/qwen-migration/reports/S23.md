## Note per le sezioni successive
- Scoperte dall'esplorazione (prima del passo 1):
  - `LanguageModelRunnerFactory.make` sceglie il runner da `Model.family(of:)`; `loadTokenizer(family:forModelDirectory:)` dà il tokenizer. Per Qwen la factory non passa `runtimeConfiguration` al runner (nota S21).
  - `runRawCompletion` usa `tokenizer.stopTokenIDs/endOfTurnID/toolResultWaitID` (protocollo `ChatTokenizer`): per Qwen `toolResultWaitID` è nil, quindi un turno con tool call termina con `.endOfTurn`, mai `.toolCalls`; `uncommittedBoundaryTokenIDs` = [im_end] (count 1, ok per il publish della cache); il bridge `QwenTokenizer.encodeTextContinuation` inizia proprio con im_end, quindi il check `boundaryMismatch` è coerente.
  - `ServerPromptCache` è legato a `GFTokenizer` per i bridge (`encodeTextContinuation`, `encodeToolResultContinuation`) e per `matchToolContinuation` che esige `rawStopReason == .toolCalls` (impossibile per Qwen). Servono: un protocollo-bridge locale al modulo server (non posso toccare TurboFieldfare: la scheda consente solo `Sources/TurboFieldfareServer/` + docs + test) con adapter Gemma/Qwen, e un check family-aware sul rawStopReason per i tool (Qwen: `.endOfTurn` con `toolCalls` non vuoti).
  - `chat_template_kwargs`: oggi è rifiutato in decode come `unknown_parameter` (lista `unsupportedKeys`/`toleratedKeys` in `OpenAIModels.swift`). PIANO: aggiungerlo tra i campi decodificati (JSONValue grezzo), e validarlo in `OpenAIRequestValidator.validate` che riceve la famiglia: Gemma → stesso errore di oggi (messaggio identico "unrecognized request field \"chat_template_kwargs\""); Qwen → solo oggetto con chiave unica `enable_thinking` booleana (decisione: le altre chiavi interne sono rifiutate, il piano non le nomina). Default enableThinking = true (U3).
  - Default sampling del validator: hardcoded Gemma 0.2/64/0.95. D10/U4 chiede default per famiglia: per Qwen 1.0/20/0.95 (come `qwenGenerationConfig` del CLI S22). Gemma invariato.
  - `ServerModelVariant`: aggiunge `family` (default .gemma4, come `CLIModelVariant`); `defaultAPIModelID` per Qwen = `manifestModelID` (D9: `mlx-community/Qwen3.6-35B-A3B-4bit`). `ServerModelVariant.read` è già family-aware (ManifestReader valida contro `ArchConfig.qwen36_35B_A3B` se c'è `modelFamily`, ManifestReader.swift:146).
  - Admission memoria in `ServerArguments` usa `ArchConfig.gemma4_26B_A4B`: la CLI fa altrettanto con Qwen (S22); lascio identico, stima conservativa; lo annoto.
  - `Tests/TurboFieldfareServer` non dichiara `TurboFieldfare` né `TurboFieldfareValidationSupport` nei deps di Package.swift (non modificabile), ma i test esistenti fanno già `@testable import TurboFieldfare`: l'import transitivo funziona in questo setup. Proverò `import TurboFieldfareValidationSupport` per `ScriptedLogitProducer`; fallback: producer scriptato locale nel file di test.
  - Fixtures Qwen per i test tokenizer: percorso `Tests/QwenFixtures` + tokenizer in `scratch/qwen36.gturbo/tokenizer` o `scratch/qwen36-tokenizer` (pattern `QwenTestResources`, gate C9: `manifest.json` presente).
  - Errore immagini Qwen (D12): messaggio esatto "image input is not available for this model"; scelta: HTTP 400, code `image_not_supported`, param `messages` (il piano fissa il messaggio, non il code).
  - `vision_pack` esplicito con Qwen: rifiutato al load ("vision is not available for this model") — fail-closed, D12.
- Scoperte del passo 2 (commit 2409147):
  - Il decodificatore Qwen (`QwenAssistantDecoder`) corre per ogni richiesta Qwen, con o senza tool: il frame think del template c'è sempre e il suo splitter è ciò che tiene il ragionamento fuori da `content` (D11). Il `StructuredAssistantDecoder` di Gemma e il check `orphanToolResponse` restano legati a `needsToolTemplate` di Gemma.
  - La famiglia arriva al validator via `TurboFieldfareHTTPServer(family:)` (da `ServerModelSession.family`, nonisolato) e al decoder della richiesta via `JSONDecoder.userInfo[OpenAIChatRequest.modelFamilyUserInfoKey]`; assente = Gemma (comportamento pre-Qwen identico, verificato nei test: messaggio/param/code invariati).
  - Il token di confine (im_end per Qwen) non entra nel KV né in `kvBackedTokenIDs` (il loop di decode fa `break` prima di append/produce sul token di stop): per questo il bridge `encodeTextContinuation` lo ri-emette e il check `boundaryMismatch` è coerente; `kvPosition` dopo una generazione pulita è esattamente la posizione del cache del runner, quindi `.resume(cachedPromptTokens:)` è legale per Qwen senza rewind (D6: la continuazione in coda alla posizione corrente funziona sempre).
  - Filtri `Scripts/test.sh --filter`: matchano il nome del tipo Swift (p.es. `ServerQwenRequestFamilyTests`), non il display name della suite.
