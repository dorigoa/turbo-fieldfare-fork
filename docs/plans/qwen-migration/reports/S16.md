## Note per le sezioni successive

- `rope_proportional_neox` di Gemma **non è richiamabile** per Qwen: il kernel
  (rope.metal) accoppia `(pair, headDim/2 + pair)` → con head_dim 256 darebbe
  coppie (i, 128+i), mentre 3.5 richiede (i, i+32) nelle prime 64 dimensioni;
  inoltre usa come divisore di frequenza `head_dim`, mentre Qwen vuole 64
  (inv_freq_i = 1e7^(-2i/64)). Serve il kernel `qwen_rope_partial` (D4).
- `Attention.encodeFull`/`splitGeometry` non usati: la via Gemma aspetta layout
  KV propri e il percorso grouped-vector è vincolato a headDim 512; il layout
  KV di D5 è `[posizione][testa KV][256]` → kernel `qwen_attention` dedicato
  (via permessa dalla scheda: "kernel qwen_ semplice e corretto").
- `q_norm`/`k_norm` riusano `QwenNorms.encodePerHead` S12 (headDim 256,
  mode `.plain` = `normWeightsShifted = true`, eps 1e-6): già testato in S12,
  qui testato solo in catena.
- Funzione: `RelError.compute(actual:reference:)`, `Fp16Buffer.make/read`,
  `SeedTree(_).key(label)`, `SplitMix64.uniform(lo,hi)` (ValidationSupport).
- API `QwenAttention` per il runner (S17+): `encodeSplitQG` (uscita q_proj
  [T][16×512] → q e gate [T][16×256]) → `QwenNorms.encodePerHead` (`.plain`)
  su q e k → `encodeRopePartial` (`positionBase` = posizione del primo token,
  32 coppie, theta 1e7, in-place) → `encodeKVWrite` (va chiamato prima di
  `encodeAttention` nello stesso command buffer: i kernel sono in ordine) →
  `encodeAttention` (decode: `queryTokens` 1, `kvStart` = posizione corrente;
  prefill: T; `scale` 1/16) → `encodeGate`. I parametri di layout
  (`posStride`/`headStride`) sono valori: S18 può dimensionare la cache a
  capacità con stride > headDim senza toccare i kernel.
- `encodeAttention` vincola `headDim ≤ 256` (un thread per dimensione,
  threadgroup da 256); GQA richiede `queryHeads % kvHeads == 0`. Buffer di
  output separati dall'input nelle prove; nessun costo di funzione usato.
